# 定位計算程式 — 跨程式介面規格

> 角色定義（先記住誰發誰收）：
> - **感測器（樹莓派）**：訂閱 `session_key`、發布 `receivers/{NO}` 封包資料 —— 只走 MQTT。
> - **定位計算程式（Python）**：接收 Node 的 HTTP、發布 `session_key`、訂閱 `receivers/{NO}` —— MQTT + HTTP（http server 兼 http client）。
> - **點名伺服器（Node.js）**：只走 HTTP，不碰 MQTT。
>
> - MQTT 是「單向發布」，沒有回信 → 只定義送出的 payload。
> - HTTP 是「一問一答」→ 每支介面同時定義「請求 + 回應」。

---

## A. HTTP — 定位計算程式收「XOR Key + OTP 對照表」（Node → 定位計算）

**目的：** 點名伺服器開始一次點名時，把本次的 XOR Key 和「學號 → OTP」對照表送給定位計算程式，並**驗證整條管道是否打通**（key 能不能解、有沒有學生真的在場）。

**發送方：** [[2.3 Node.js 主程式 API]]（http client）
**接收方：** 定位計算程式（localhost http server）

| 項目 | 值 |
|------|-----|
| Method | `POST` |
| Path | `/api/session/config` |
| Host / Port | `http://127.0.0.1:{定位計算 port}`（port 待定，例如 8020） |
| Content-Type | `application/json; charset=UTF-8` |
| 同步等待 | 收到有效封包即回，最長等 `timeout` 秒（建議 5 秒） |

### Request Body
```json
{
    "session_id": "sess_20260909_01",
    "xor_key": "TEST_KEY_2024",
    "otp_list": {
        "11012345": "A1B2C3",
        "11012346": "D4E5F6",
        "11012347": "G7H8I9",
        "11012348": "J0K1L2"
    }
}
```

### Request 欄位
| 欄位 | 型態 | 必填 | 說明 |
|------|------|------|------|
| `session_id` | string | 是 | 本次點名 session 的唯一識別 |
| `xor_key` | string | 是 | 本次共用 XOR 加密金鑰（pub 到 MQTT 用） |
| `otp_list` | object | 是 | key = 8 位學號，value = 該生 OTP。空物件視為不存在 |

### 定位計算程式收到後做的事（依序）
1. 把收到的 `xor_key` 資料以 MQTT publish 至 `session_key`（retained），供感測器訂閱解密。
2. 訂閱 `receivers/{RECEIVER_NO}`，等待 **「第一個有效封包」**（見 §C：`student_id ∈ otp_list` **且** OTP 相符）。
3. 以該封包解出的學號去 `otp_list` 查出「應該的 OTP」，並與該封包攜帶的 OTP 比對。
4. 比對一致 → 回 ok；比對不一致或等不到有效封包逾時 → 回 failed。
5. **OTP 不一致的封包會被整筆丟棄**（不進定位引擎、不產生座標），以免用到可能錯誤的學號。

### Response Body（一問一答，只回一次）

成功（第一個有效封包 OTP 相符）→ `200 OK`：
```json
{ "status": "ok", "session_id": "sess_20260909_01", "student_id": "11012345" }
```

失敗（OTP 不符）→ `400 Bad Request`：
```json
{ "status": "failed", "session_id": "sess_20260909_01", "reason": "otp_mismatch" }
```

逾時（等不到有效封包）→ `504 Gateway Timeout`：
```json
{ "status": "failed", "session_id": "sess_20260909_01", "reason": "timeout" }
```

格式錯誤 → `400 Bad Request`：
```json
{ "status": "failed", "reason": "invalid_body", "message": "缺少欄位或 JSON 解析失敗" }
```

## B. HTTP — 定位計算程式主動送座標（定位計算 → Node）

**目的：** 每個算好座標的有效學生，主動送回點名伺服器更新。此介面在一次 session 內可**連續呼叫多次（一個學生一次）**。

**發送方：** 定位計算程式（http client）
**接收方：** [[2.3 Node.js 主程式 API]]（點名伺服器 http server）

| 項目 | 值 |
|------|-----|
| Method | `POST` |
| Path | `/api/coords`（依 Node 端既有 API 命名調整） |
| Host / Port | `http://127.0.0.1:{Node port}`（與 §A 同機不同 service） |
| Content-Type | `application/json; charset=UTF-8` |

> 觀念：§A 那次的 response（ok/failed）已經回完、結束了。**座標是另一支 request**，不可能回給同一支。

### Request Body
```json
{
    "session_id": "sess_20260909_01",
    "student_id": "11012345",
    "x": 12,
    "y": 20,
    "coordinate_system": "grid32",
    "timestamp": "09/09/2026 14:30:22"
}
```

### Request 欄位
| 欄位 | 型態 | 必填 | 說明 |
|------|------|------|------|
| `session_id` | string | 是 | 對應 §A 建立的 session |
| `student_id` | string | 是 | 8 位學號 |
| `x` | int / float | 是 | 座標 X |
| `y` | int / float | 是 | 座標 Y |
| `coordinate_system` | string | 是 | 座標單位。`grid32` = 0~31 格點 / `meter` = 公尺，二擇一 |
| `timestamp` | string | 是 | `dd/mm/yyyy HH:MM:SS`（NTP 同步後時間） |

**「有效座標」的定義（決定是否回 ok）：**
1. `session_id`、`student_id`、`x`、`y`、`coordinate_system` 欄位齊全且型態正確。
2. `student_id` 是本次 session 內**已通過 OTP 驗證**的學生
   （依 §C 嚴格模式：該生的封包必為「學號在名單 + OTP 相符」，否則不會被定位）。
3. 若 `coordinate_system = grid32`，需 `0 ≤ x, y ≤ 31`；若 `meter`，需在教室允許範圍內。
4. （可選）以「3 台（含）以上接收到的 RSSI」算出的座標才算有效。

### Response Body

有效座標，接受 → `200 OK`：
```json
{ "status": "ok", "accepted": true }
```

無效座標 → `400 Bad Request`：
```json
{ "status": "failed", "reason": "invalid_coord", "message": "…" }
```

## C. MQTT — 感測器發布 RSSI 封包（感測器 → 定位計算程式）※輸入

**發送方：** 感測器（樹莓派）publish
**接收方：** 定位計算程式 subscribe

| Topic | 方向 |
|-------|------|
| `{topic}/receivers/{RECEIVER_NO}` | 感測器 → Broker → 定位計算程式 |

Payload（json）：
```json
{
    "student_id": "11012345",
    "OTP": "A1B2C3",
    "mac": "B4E7B36041B4",
    "rssi": -72,
    "scanner_id": 1,
    "time": "09/09/2026 14:30:22"
}
```

| 欄位 | 型態 | 說明 |
|------|------|------|
| `student_id` | string | 8 位學號（封包 XOR 解密取得）★ **唯一識別，定位引擎的 key** |
| `OTP` | string | 該學生 beacon 內嵌 OTP（與 §A otp_list 對照） |
| `mac` | string | 手機 BLE MAC（大寫無分隔）。**僅供除錯/顯示，不可作為識別**（MAC 會隨機化變動） |
| `rssi` | int | 原始 RSSI（濾波留給定位計算端） |
| `scanner_id` | int | 樹莓派編號 |
| `time` | string | `dd/mm/yyyy HH:MM:SS`（NTP 同步後） |

> ⚠️ **「有效封包」的定義（嚴格模式，2026-09 決議）**：
> 必須 **`student_id ∈ otp_list` 且其對應 OTP 相符**，兩個條件**同時成立**才算有效封包。
>
> 理由：OTP 對不上可能代表「XOR key 沒更新 / App 用了舊的 OTP」，
> 此時解出的學號也可能是錯的——若拿來定位會污染別人的位置。
> 因此 **OTP 不通過的封包一律丟棄、不進定位引擎、不產生座標**，
> 而 §A 的回應即為 `failed` / `reason: "otp_mismatch"`。

---

## D. MQTT — 定位計算程式發布 Session XOR Key（定位計算 → 感測器）※輸出

**發送方：** 定位計算程式 publish（源自 §A 收到的 xor_key）
**接收方：** 感測器 subscribe（retained，新開機的感測器也能立刻取到）

| Topic | QoS | Retained |
|-------|-----|----------|
| `{topic}/session_key` | 1 | 是 |

Payload（json）：
```json
{ "xor_key": "TEST_KEY_2024" }
```

> ⚠️ 欄位統一用小寫 `xor_key`（與 §A 相同），各文件不要再混用不同大小寫。

---

## 生命週期串接（把 A+B+C+D 串起來）

```
Node ──POST A(config: xor+otp)──▶ 定位計算
定位計算 ──MQTT D(session_key)──▶ 感測器
感測器 ──MQTT C(receivers)──▶ 定位計算   ← 等「第一個有效封包」（學號在 otp_list 且 OTP 相符）
定位計算 ──比對 OTP，HTTP A response──▶ Node (ok / failed)
之後：定位計算 ──HTTP B(coords 某生)──▶ Node（每個學生的座標都是獨立一支 request）
```
