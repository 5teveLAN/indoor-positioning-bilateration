### 架構設計

#### 通訊協定的設計
![[file-20260909091423786.png]]
1. 假設這整套系統都是連結同一個學校網路，分為感測器、App, 伺服器
2. App 如何連線到 點名伺服器： 
	- 老師/同學 可能使用自己的網路，所以必須透過 Internet，目前透過 ngrok 中轉
3. 感測器 如何連線到 點名伺服器： 
	- 是同一個學校網路，但面臨以下問題：
		- 不同 AP 有沒有隔離？
		- mqtts (8883) 會不會被擋？
		- Broker IP 會變，憑證又綁定 IP
		- 可能要搞 mDNS，但問題又是 mDNS 會不會被檔
		- 我沒任何網管權限
	- 為求方便，也是透過第三方中轉
	
4. 後端伺服器內部通訊：因為來不及學 JS，採用py+js，然後透過 http 伺服器進行本地溝通

- 因為定位系統是附加於主系統之外的服務，故希望原本的 點名伺服器 和 App 不需額外撰寫 Mqtt 程式，只需在原有的 http 下添加程式碼溝通即可。
 - 目前我在我的電腦進行黃色部分程式的開發，開發完成後在部屬到伺服器。
#### 資料流向圖 (紅色箭頭為上未完成的部分)
 ![[file-20260908164850631.png]]
XOR key 的流程 (xor key 紅色路徑) —— 這其實是兩支獨立的 API：

**API-A（驗證管道用，只做一次）：** 點名伺服器 → 定位計算程式（HTTP 請求）
1. Node 送 request（含 xor_key + otp_list）給定位計算程式
2. 定位計算把 xor_key 丟給感測器（MQTT publish session_key）
3. 感測器用它解密，並把封包資料發回給定位計算（MQTT receivers/{NO}）
4. 定位計算等「第一個『學號存在於 otp_list 內』」的封包，拿解出的學號去 otp_list 查「應該的 OTP」並比對
	1. 相符 → HTTP response 回 ok
	2. 不符 → HTTP response 回 failed
	3. 超過 timeout（建議 5 秒）沒等到有效封包 → HTTP response 回 failed(timeout)
   （這就是 [[2.2.1 定位計算程式 — 跨程式介面規格]] 的 §A）

**API-B（算座標用，OK 後連續多次）：** 定位計算程式 → 點名伺服器（HTTP 請求）
5. 每次算好一個有效學生的座標，定位計算就主動 POST 給 Node
   （這就是 [[2.2.1 定位計算程式 — 跨程式介面規格]] 的 §B）
   ※ 感測器本身不會因為 ok/failed 而停掃；「決定要不要算座標」只發生在定位計算這一側。

> ⚠️ OK 的判定 = 管道能解 key 且至少有 1 位學生在場，不是「全班到齊」。
