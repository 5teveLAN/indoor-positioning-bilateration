### 1.1 老師：開始點名 Session

取得本次點名的 XOR Key。

```
POST /api/session/start
```

**Request Body：**
```json
{
    "email": "teacher@example.com",
    "password": "老師密碼"
}
```

| 欄位 | 型態 | 必填 | 說明 |
|------|------|------|------|
| `email` | string | 是 | 老師帳號 |
| `password` | string | 是 | 老師密碼（**必填**，見下方說明） |

> ⚠️ **所有「老師專用」的 request 都必須帶 `password`**（1.1、1.2、2.2 若由老師發、2.4）。
> 沒有帶或驗證失敗 → 一律回 `401 Unauthorized`，**不得執行任何動作**。
> 這裡只是規格上的明文欄位，實際傳輸走 HTTPS，且伺服器端必須比對雜湊後的值。

**Response Body（200 OK）：**
```json
{
    "xor_key": "TEST_KEY_2024",
    "session_id": "sess_20260909_01"
}
```

> `xor_key` 為本次 Session 所有學生共用的 XOR 加密金鑰。
> `session_id` 由伺服器產生，是後續 2.2 / 2.4 的查詢依據，**必須不可預測**（見下方警告）。

**失敗（401 Unauthorized）：**
```json
{
    "status": "failed",
    "reason": "invalid_credentials",
    "message": "帳號或密碼錯誤"
}
```

> ⚠️ **`session_id` 必須是不可預測的隨機值**（例如 UUID v4 或 128-bit 隨機 hex），
> **不可用 `sess_20260909_01` 這種「日期 + 流水號」格式**。
> 理由：`session_id` 是 [2.2](#22-app取得本次點名所有學生座標app--node) 的存取憑證之一，
> 可預測就等於把全班座標的門打開（IDOR 漏洞）。

**⚠️ 這個接口成功後，Node 必須再接兩件事**（詳見 [2.0 資料流與設計原則](#20-資料流與設計原則)）：

1. 呼叫 [1.2 取得 OTP 對照表](#12-老師取得-otp-驗證對照表) 拿到 `otp_list`。
2. 把 `session_id` + `xor_key` + `otp_list` 用 HTTP `POST /api/session/config` **送給定位計算程式**（規格見 [[2.2.1 定位計算程式 — 跨程式介面規格]] §A），同時**清空上次的座標暫存 buffer**（見 [2.3](#23-座標暫存buffer資料結構)）。

> 定位計算程式收到後才會把 `xor_key` 以 MQTT 發布給感測器，並開始產生座標。
> **Node 本身不碰 MQTT**，所有與感測器、定位引擎的通訊都由定位計算程式負責。

---

### 1.2 老師：取得 OTP 驗證對照表

取得全班學號與 OTP 的對照表。

> ⚠️ **這支是全系統最敏感的接口之一**：拿到 `otp_list` 就能偽造任意學生的簽到。
> 因此**必須驗證老師身分**（`email` + `password`），缺一不可。

```
POST /api/session/otp-list
```

**Request Body：**
```json
{
    "email": "teacher@example.com",
    "password": "老師密碼"
}
```

| 欄位 | 型態 | 必填 | 說明 |
|------|------|------|------|
| `email` | string | 是 | 老師帳號 |
| `password` | string | 是 | 老師密碼 |

**Response Body（200 OK）：**
```json
{
    "otp_list": {
        "11012345": "A1B2C3",
        "11012346": "D4E5F6",
        "11012347": "G7H8I9",
        "11012348": "J0K1L2"
    }
}
```

> key = 學號, value = 該學生的 OTP。

**失敗（401 Unauthorized）：**
```json
{
    "status": "failed",
    "reason": "invalid_credentials",
    "message": "帳號或密碼錯誤"
}
```

> ⚠️ 驗證失敗時**只回 401**，不可回「帳號存在但密碼錯」之類的差異訊息
> （避免帳號列舉）。

## 2. 跟定位有關的 API

### 2.0 資料流與設計原則

**角色分工（誰發誰收）：**

| 角色 | 通訊方式 | 說明 |
|------|----------|------|
| App | HTTP → Node | 上傳自身 beacon 用的 OTP/XOR Key、向 Node **拉取**全班座標 |
| Node（點名伺服器） | HTTP only | 接收座標、**暫存**、回應 App。**不碰 MQTT** |
| 定位計算程式 | HTTP + MQTT | 收 Node 的 session 設定、算座標、把座標**推**回 Node |
| 感測器 | MQTT only | 訂閱 `session_key`、發布 `receivers/{NO}` RSSI 封包 |

**核心設計：座標先蒐集、App 再來拉（Push → Buffer → Pull）**

```
定位計算 ──POST /api/coords（一個學生一支）──▶ Node
                                                │
                                                ▼
                                       座標暫存 buffer（in-memory）
                                       以 (session_id, student_id) 為 key
                                       同一學生重複上傳 → 覆蓋（取最新）
                                                │
App ──POST /api/coords/get（帶 session_id）────▶ Node
                                       Node 一次回「目前 buffer 內所有學生的座標」
```

**為什麼要 buffer，而不是定位算完直接推給 App？**

1. **App 與定位計算沒有直接連線**：定位計算只認 Node，App 也只認 Node，Node 是唯一交會點。
2. **座標是陸續產生的**：每個學生的封包在不同時間到達、定位引擎陸續算出座標，
   而 App 可能是「進到座位圖頁面時」才想看全部人的位置 → 需要有人先蒐集起來。
3. **一問一答（Pull）比被動接收（Push）對 App 簡單**：
   App 不用長連線（WebSocket / SSE），只要在需要時打一支 API 把整張圖一次拿回來畫。
4. **同一學生會有多筆座標**：定位是持續更新的，buffer 用 `student_id` 當 key **覆蓋**，
   永遠只保留「該生最新座標」，避免 App 拿到重複或過期的資料。

**API 清單：**

| 編號 | Method | Path | 方向 | 用途 | 需要老師帳密 |
|------|--------|------|------|------|:---:|
| 2.1 | `POST` | `/api/coords` | 定位計算 → Node | 上傳單一學生座標（可連續呼叫多次） | ❌（限內網） |
| 2.2 | `POST` | `/api/coords/get` | App → Node | 取得本次點名**所有**學生座標 | ✅ |
| 2.4 | `POST` | `/api/coords/clear` | 老師 → Node | 清除本次 session 的暫存座標 | ✅ |

**🔒 存取控制原則（重要）：**

| 接口 | 暴露範圍 | 保護方式 |
|------|----------|----------|
| 2.1 `/api/coords` | **僅限本機 `127.0.0.1`**，**不可**透過 ngrok / 對外網域開放 | 網路層隔離（綁 `127.0.0.1`、防火牆） |
| 2.2 `/api/coords/get` | 對外（App 要用） | 老師 `email` + `password` + session 擁有者檢查 |
| 2.4 `/api/coords/clear` | 對外（老師 App 要用） | 同上 |

> ⚠️ **HTTPS 不是授權機制。**
> HTTPS 只保護「傳輸過程」，無法阻止攻擊者**自己合法地**送出請求。
> 只要接口沒有驗證「你是誰、你能不能碰這筆資料」，任何知道參數的人都能拿到機密資訊。
> 這類漏洞統稱 **IDOR / Broken Object Level Authorization（OWASP API1:2023）**。
>
> 因此判斷原則很簡單：
> **凡是回傳「別人的資料」或「能改動別人狀態」的接口，都必須驗身分，不能只靠一個 ID 參數。**



---

### 2.1 定位計算程式：上傳座標（定位計算 → Node）

**目的：** 定位計算程式每算好一個學生的座標，就主動推回 Node 暫存。
此接口在一次 session 內可**連續呼叫多次（一個學生一次）**。

> 本節對應 [[2.2.1 定位計算程式 — 跨程式介面規格]] 的 §B，兩份文件需保持一致。

```
POST /api/coords
```

| 項目 | 值 |
|------|-----|
| Host / Port | `http://127.0.0.1:{Node port}`（與定位計算同機、不同 service） |
| Content-Type | `application/json; charset=UTF-8` |
| 呼叫時機 | 每次算完一個學生座標時（同一學生更新會再呼叫一次） |
| 暴露範圍 | 🔒 **只綁 `127.0.0.1`，不對外開放** |

> 🔒 **本接口是內部接口，絕對不可暴露到公網。**
> 它沒有任何身分驗證（因為呼叫者是同機的定位計算程式），
> 若被外部打進來，攻擊者可**任意偽造學生的座標**（製造假簽到 / 製造不在場證明）。
>
> 實作要求：
> 1. Node 只 `listen` 在 `127.0.0.1`（不要 `0.0.0.0`）。
> 2. **不要**把這條路徑掛到 ngrok / 對外網域後面。
> 3. 若未來必須跨機器，改用共享密鑰（`X-Internal-Token`）或 mTLS，勿直接開放。

**Request Body：**
```json
{
    "session_id": "sess_20260909_01",
    "student_id": "11012345",
    "x": 12,
    "y": 20,
    "coordinate_system": "grid32",
    "timestamp": "09/09/2026 14:30:22"
}
```

**Request 欄位：**

| 欄位 | 型態 | 必填 | 說明 |
|------|------|------|------|
| `session_id` | string | 是 | 對應 [1.1](#11-老師開始點名-session) 建立的 session；不存在視為無效 |
| `student_id` | string | 是 | 8 位學號，**buffer 的 key** |
| `x` | int / float | 是 | 座標 X |
| `y` | int / float | 是 | 座標 Y |
| `coordinate_system` | string | 是 | 座標單位。`grid32` = 0~31 格點 / `meter` = 公尺，二擇一 |
| `timestamp` | string | 是 | `dd/mm/yyyy HH:MM:SS`（NTP 同步後時間），保留原始量測時間 |

> 定位計算程式**不需要**送 `otp`、`mac`、`rssi`。
> 只有「已通過 OTP 驗證」的學生才會被定位（嚴格模式，見 [[2.2.1 定位計算程式 — 跨程式介面規格]] §C），
> 因此能到達這支 API 的 `student_id` 本身就已經是被信任的。

**Node 收到後做的事（依序）：**

1. 驗證欄位是否齊全、型態是否正確。
2. 檢查 `session_id` 是否為**目前進行中的 session**。
3. 依 `coordinate_system` 檢查座標範圍（`grid32`：`0 ≤ x, y ≤ 31`；`meter`：教室允許範圍內）。
4. 以上皆通過 → 以 `(session_id, student_id)` 為 key **寫入／覆蓋** buffer（見 [2.3](#23-座標暫存buffer資料結構)），回 `200 OK`。
5. 任一項不通過 → **丟棄該筆、不寫入 buffer**，回 `400 Bad Request`。

**Response Body（200 OK）：**
```json
{
    "status": "ok",
    "accepted": true
}
```

**無效座標（400 Bad Request）：**
```json
{
    "status": "failed",
    "reason": "invalid_coord",
    "message": "session_id 不存在或座標超出範圍"
}
```

**格式錯誤（400 Bad Request）：**
```json
{
    "status": "failed",
    "reason": "invalid_body",
    "message": "缺少欄位或 JSON 解析失敗"
}
```

> ⚠️ 座標**只寫入、不即時通知 App**。App 何時拿得到，取決於它自己來打 [2.2](#22-app取得本次點名所有學生座標app--node)。

### 2.2 App：取得本次點名所有學生座標（App → Node）

**目的：** App 向 Node **一次拉回本次 session 內、目前 buffer 中所有學生的最新座標**，
用來畫座位圖／顯示每個人的位置。

> 🔒 **本接口必須驗證身分。**
> 「全班學號 + 即時座標」等於「誰坐在哪、誰不在場」，屬於機密資訊。
> 只有帶 `session_id` 就開放，任何人猜到/撈到 `session_id` 就能把全班位置全部拉走
> ——這是典型的 **IDOR / Broken Object Level Authorization**（OWASP API1:2023），
> **HTTPS 完全擋不住**（攻擊者是「合法地」送出請求，伺服器會正常回他資料）。
>
> 因此 Request 內**必須附上老師帳密**，伺服器驗證通過才回資料。

```
POST /api/coords/get
```

**Request Body：**
```json
{
    "email": "teacher@example.com",
    "password": "老師密碼",
    "session_id": "sess_20260909_01"
}
```

**Request 欄位：**

| 欄位 | 型態 | 必填 | 說明 |
|------|------|------|------|
| `email` | string | 是 | 老師帳號 |
| `password` | string | 是 | 老師密碼 |
| `session_id` | string | 是 | 要查詢的點名 session |

**Server 端驗證順序（任一失敗即中止）：**

1. `email` / `password` 是否正確 → 否則 `401 Unauthorized`。
2. 該老師**是否為這個 session 的擁有者** → 否則 `403 Forbidden`。
   （避免 A 老師拿自己的帳密去查 B 老師的班級座標。）
3. `session_id` 是否存在 → 否則 `404 Not Found`。
4. 全數通過才回 `coords` 全表。

**Response Body（200 OK）：**
```json
{
    "session_id": "sess_20260909_01",
    "coordinate_system": "grid32",
    "count": 2,
    "updated_at": "09/09/2026 14:30:25",
    "coords": {
        "11012345": { "x": 12, "y": 20, "timestamp": "09/09/2026 14:30:22" },
        "11012346": { "x": 4,  "y": 7,  "timestamp": "09/09/2026 14:30:24" }
    }
}
```

**Response 欄位：**

| 欄位 | 型態 | 說明 |
|------|------|------|
| `session_id` | string | 回音，方便 App 確認查的是同一場點名 |
| `coordinate_system` | string | 本次所有座標的單位（`grid32` / `meter`） |
| `count` | int | `coords` 內有幾位學生（＝已收到座標的人數） |
| `updated_at` | string | Node 產生這份回應的時間（`dd/mm/yyyy HH:MM:SS`） |
| `coords` | object | key = 學號，value = 該生**最新**座標 |

**`coords` 內每筆的欄位：**

| 欄位 | 型態 | 說明 |
|------|------|------|
| `x` | int / float | 座標 X |
| `y` | int / float | 座標 Y |
| `timestamp` | string | 該筆座標的量測時間（由定位計算程式提供） |

**尚無任何座標時（200 OK，不是錯誤）：**
```json
{
    "session_id": "sess_20260909_01",
    "coordinate_system": "grid32",
    "count": 0,
    "updated_at": "09/09/2026 14:30:02",
    "coords": {}
}
```

> 座標是**陸續**進來的，App 第一次拉可能只有少數幾人（甚至 0 人），
> 這是正常狀態 → 回 `200 OK` + 空物件，**不要回 404**。
> App 端可自行決定要不要隔幾秒重拉一次（polling）。

**身分驗證失敗（401 Unauthorized）：**
```json
{
    "status": "failed",
    "reason": "invalid_credentials",
    "message": "帳號或密碼錯誤"
}
```

**非本人 session（403 Forbidden）：**
```json
{
    "status": "failed",
    "reason": "forbidden",
    "message": "此 session 不屬於該老師"
}
```

**Session 不存在（404 Not Found）：**
```json
{
    "status": "failed",
    "reason": "session_not_found",
    "message": "查無此 session_id"
}
```

**格式錯誤（400 Bad Request）：**
```json
{
    "status": "failed",
    "reason": "invalid_body",
    "message": "缺少欄位或 JSON 解析失敗"
}
```

> 「該 session 已存在但還沒有任何座標」與「查無此 session」要分開：
> 前者回 `200 OK` + `coords: {}`，後者才回 `404`。

> 📌 **課堂以外的強化選項（若之後有需要）**
> 每次請求都帶明碼密碼不是長久之計，建議改為：
> 1. App 用 [1.4 登入](#14-登入) 換一張 **token**，之後所有 API 改帶 `Authorization: Bearer <token>`。
> 2. `session_id` 維持隨機不可預測 + 綁定老師身分（兩層防護）。
> 3. 限制同一帳號的請求頻率（rate limit），避免被暴力嘗試密碼或大量爬取座標。
>
> 現階段先用「帳密 + session 擁有者檢查」把洞補起來即可。

		### 2.3 座標暫存（Buffer）資料結構

**位置：** Node 主程式記憶體（in-memory），**不落地資料庫**。
理由：座標是「一次點名期間」的即時資料，點名結束即失去意義。

**結構（概念）：**

```js
// 以 session_id 分開存，避免不同場點名互相污染
const coordBuffer = {
    // session_id
    "sess_20260909_01": {
        coordinateSystem: "grid32",
        updatedAt: "09/09/2026 14:30:25",
        students: {
            // student_id → 最新一筆座標（重複上傳直接覆蓋）
            "11012345": { x: 12, y: 20, timestamp: "09/09/2026 14:30:22" },
            "11012346": { x: 4,  y: 7,  timestamp: "09/09/2026 14:30:24" }
        }
    }
};
```

| 層級 | Key | Value | 說明 |
|------|-----|-------|------|
| 第一層 | `session_id` | 該次點名的 buffer | 每次 [1.1 開始點名](#11-老師開始點名-session) 時**先清空**再建立 |
| 第二層 | `student_id` | 最新座標物件 | **覆蓋語意**：同一學生再上傳就取代舊的，不累積歷史 |
| 座標物件 | — | `{ x, y, timestamp }` | `x`/`y` 為該生最新位置，`timestamp` 為量測時間 |

**行為規則：**

| 情境 | 行為 |
|------|------|
| 新 session 開始（1.1 成功） | 為該 `session_id` 建立空 buffer（若已存在則清空重來） |
| 收到 2.1 座標，該生尚未有紀錄 | 直接寫入 |
| 收到 2.1 座標，該生已有紀錄 | **覆蓋**舊座標（只保留最新） |
| 同一 session 換了 `coordinate_system` | 以最新一筆為準，2.2 回應的 `coordinate_system` 隨之更新 |
| session 結束／老師按下結束 | 呼叫 [2.4](#24-老師清除本次定位資料) 清掉該 session 的 buffer |
| Node 重啟 | buffer 清空（in-memory 特性）；點名需重新走 1.1 開始 |

> ⚠️ **`coordBuffer` 不會自動長大也不會自動縮小**，
> 因此務必在「新 session 開始」與「session 結束」各清一次，避免舊資料被下一場點名查到。

### 2.4 老師：清除本次定位資料

**目的：** 一次點名結束時，把該 session 暫存的座標全部丟掉，避免殘留或外洩。

> 🔒 **同 [2.2](#22-app取得本次點名所有學生座標app--node)，本接口也必須驗證老師身分。**
> 否則任何人只要知道 `session_id` 就能**清掉老師正在進行中的點名資料**（阻斷服務）。

```
POST /api/coords/clear
```

**Request Body：**
```json
{
    "email": "teacher@example.com",
    "password": "老師密碼",
    "session_id": "sess_20260909_01"
}
```

**Request 欄位：**

| 欄位 | 型態 | 必填 | 說明 |
|------|------|------|------|
| `email` | string | 是 | 老師帳號 |
| `password` | string | 是 | 老師密碼 |
| `session_id` | string | 是 | 要清除的點名 session |

**Server 端驗證順序（與 2.2 相同）：**

1. `email` / `password` 是否正確 → 否則 `401 Unauthorized`。
2. 該老師是否為本 session 的擁有者 → 否則 `403 Forbidden`。
3. 通過才執行清除。

**Response Body（200 OK）：**
```json
{
    "status": "ok",
    "session_id": "sess_20260909_01",
    "cleared": 4
}
```

| 欄位 | 型態 | 說明 |
|------|------|------|
| `status` | string | `ok` = 已清除 |
| `session_id` | string | 回音 |
| `cleared` | int | 這次清掉了幾位學生的座標 |

> 若該 session 本來就沒有資料，回 `200 OK` 且 `cleared: 0`
> （視為 idempotent，重複呼叫不報錯）。

**身分驗證失敗（401 Unauthorized）：**
```json
{
    "status": "failed",
    "reason": "invalid_credentials",
    "message": "帳號或密碼錯誤"
}
```

**非本人 session（403 Forbidden）：**
```json
{
    "status": "failed",
    "reason": "forbidden",
    "message": "此 session 不屬於該老師"
}
```

### 2.5 定位 API 時序圖（完整串接）

```
老師 App ──POST /api/session/start（email+password）───▶ Node （1.1，取得 xor_key + session_id）
老師 App ──POST /api/session/otp-list（email+password）▶ Node （1.2，取得 otp_list）
                                        Node ──清空 coordBuffer[session_id]──┐
                                        Node ──POST /api/session/config────▶ 定位計算（2.2.1 §A）
                                                                            定位計算 ──MQTT publish session_key──▶ 感測器
                                                                            感測器   ──MQTT receivers/{NO}──▶ 定位計算
                                                                            定位計算 ──HTTP A response(ok)──▶ Node
定位計算 ──POST /api/coords（學生A）───▶ Node ──覆蓋 buffer──┐   ← 限 127.0.0.1
定位計算 ──POST /api/coords（學生B）───▶ Node ──覆蓋 buffer──┤  ← 2.1，陸續進來
定位計算 ──POST /api/coords（學生A 更新）▶ Node ──覆蓋 buffer┘
App      ──POST /api/coords/get（email+password+session_id）▶ Node ──回 coords 全表──▶ App （2.2）
老師 App ──POST /api/coords/clear（email+password+session_id）▶ Node ──清空 buffer      （2.4）
```

| 步驟 | API | 方向 | 驗身分 | 備註 |
|------|-----|------|:---:|------|
| 1 | [1.1 `/api/session/start`](#11-老師開始點名-session) | 老師 App → Node | ✅ | 拿 `xor_key` + `session_id` |
| 2 | [1.2 `/api/session/otp-list`](#12-老師取得-otp-驗證對照表) | 老師 App → Node | ✅ | 拿 `otp_list`（敏感） |
| 3 | `POST /api/session/config` | Node → 定位計算 | — | 規格見 [[2.2.1 定位計算程式 — 跨程式介面規格]] §A |
| 4 | [2.1 `/api/coords`](#21-定位計算程式上傳座標定位計算--node) | 定位計算 → Node | ❌（限內網） | 一位學生一支，可多次 |
| 5 | [2.2 `/api/coords/get`](#22-app取得本次點名所有學生座標app--node) | App → Node | ✅ | App 想要位置時就打一次 |
| 6 | [2.4 `/api/coords/clear`](#24-老師清除本次定位資料) | 老師 App → Node | ✅ | 點名結束清除 |

> 步驟 4 與 5 沒有固定先後，是**持續交錯**發生的：
> 定位計算一直推、App 一直拉，Node 的 buffer 就是兩者之間的橋樑。

### 2.6 安全檢查表（上線前逐項確認）

| # | 檢查項 | 為什麼 |
|---|--------|--------|
| 1 | 1.1 / 1.2 / 2.2 / 2.4 都驗證 `email` + `password` | 否則任何人可取得 OTP 表與全班座標 |
| 2 | 2.2 / 2.4 額外檢查「session 擁有者」 | 防止 A 老師查/清 B 老師的班級 |
| 3 | `session_id` 使用不可預測的隨機值 | 防止掃流水號直接存取 |
| 4 | 2.1 `/api/coords` 只綁 `127.0.0.1`、不掛對外 | 防止偽造座標 |
| 5 | 密碼絕不明文存 DB，一律雜湊（bcrypt/argon2） | 資料庫外洩時的最後防線 |
| 6 | 驗證失敗一律回 `401`，不回差異訊息 | 防止帳號列舉 |
| 7 | 對 1.1 / 1.2 / 2.2 加 rate limit | 防止暴力猜密碼 / 大量爬座標 |
| 8 | 點名結束務必呼叫 2.4 清 buffer | 資料最小化，避免殘留 |
| 9 | 傳輸全程 HTTPS（ngrok 已提供） | 防止中途竊聽帳密 |
| 10 | 建議後續改為 token 機制（Bearer） | 避免每次請求都傳明碼密碼 |

> 💡 **第 10 點是最終方向**：目前「每次請求帶帳密」是把洞補起來的**過渡方案**，
> 正式做法是 [1.4 登入](#14-登入) 後發一張有時效的 token，
> 之後所有需要身分的接口改帶 `Authorization: Bearer <token>`。
